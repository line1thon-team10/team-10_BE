## 2. task 정의

한 task는 한 에이전트가 책임지고 **하나의 검증 가능한 결과**를 넘기는 단위다. 다음 정보가 없는 task는 배정하지 않는다.

| 항목 | 의미 |
|---|---|
| id/title | 예: R-02 범위별 기록 저장·정정 API |
| depends_on | 착수 전 `integrated`가 되어야 하는 선행 task |
| write_scope | 수정 가능한 경로. 저장소 루트 이름은 worker의 해당 worktree로 치환 |
| shared_resources | 경로와 별도로 경합하는 migration, 기존 서비스 등 |
| integration_only_paths | 기본적으로 오케스트레이터가 관리하는 등록·공통 파일 |
| deliverable/acceptance | 결과물과 필수 정상·엣지케이스 |
| operations/contract_files | 담당 API와 판단 근거. 없는 API를 임의로 추가하지 않음 |
| external_gates | 실제 자격·정책·자료 확인이 필요한 부분. task별로만 적용 |
| base_sha/head_sha/branch/pr_url | 실제 검토한 코드 식별자 |
| validation_evidence | 명령·환경·결과·검증한 SHA. 단순 '통과' 메시지로 대체하지 않음 |

task 하나에 여러 독립 목적이 드러나면 배정 전에 하위 task로 나눈다. 이미 사용한 ID를 재사용하지 않고 새 ID와 의존성을 등록한다. O-03/FE 흐름처럼 관련 endpoint를 함께 다루는 task도 커밋은 각 독립 변경으로 나눈다. DB 영속 구조와 API 동작을 한꺼번에 묶지 말고, migration+해당 테스트가 독립적으로 완성되면 먼저 커밋한다.

## 3. 역할과 슬롯

오케스트레이터 1 + 실행/검토 에이전트 최대 3을 사용한다.

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| 오케스트레이터 | 다음 task 선정, 범위·파일 소유권, 정책 판단, 공통 변경 조율, 리뷰 판정, 통합·배포 | 검증 전 완료 선언, 전체 기능을 혼자 동시에 구현 |
| 실행 에이전트 | 한 번에 task 하나, 담당 코드·테스트·원자 커밋·인수인계 | 다른 작업트리 변경, 임의 공통 리팩터링, main/운영 변경, 독자적인 하위 에이전트 추가 |
| 검토 에이전트 | 구현자가 아닌 관점으로 immutable diff와 명세·엣지케이스 검토, 한국어 결과 | 검토 중 구현자 브랜치 직접 수정, 테스트 통과를 무조건 승인으로 간주 |

첫 착수 때는 실행 3개를 병렬로 돌릴 수 있다. 첫 완료물이 나오면 **실행 2 + 검토 1**로 바꾸고, 검토 대기가 없을 때 세 번째 실행 task를 넣는다. 특정 에이전트가 한 작업축 전체를 독점하지 않는다. task가 끝나면 의존성과 파일 충돌에 따라 슬롯을 재배정한다. 모델/effort는 별도 사용자 지시가 없으면 기본 상속을 사용한다.

## 4. 배정 판단

다음 조건을 모두 만족해야 구현을 시작한다.

1. 선행 task가 실제 통합 SHA에 포함되어 있다. 단순 계획/fixture/미병합 PR을 완료 의존성으로 취급하지 않는다.
2. task의 외부 조건이 해소되었거나, 그것에 의존하지 않는 독립 task로 먼저 분리했다.
3. 다른 활성 task와 `write_scope`의 파일 또는 디렉터리 prefix가 겹치지 않는다. worktree가 달라도 논리적으로 같은 파일은 같은 자원이다.
4. `shared_resources` 및 통합 전용 경로에 대한 변경 소유권이 확보되었다.
5. 명세, 기준 SHA, 테스트 명령, 완료 조건을 전달했다.

선행 구현을 기다리는 동안 테스트 사례·계약 검토·읽기 전용 설계는 가능하다. 다만 이를 실제 구현 완료나 `integrated`로 표시하지 않는다. 정책 하나가 미정이어도 관련 없는 task 전체를 세우지 않는다. 예를 들어 OCR 정책 POL-03은 M-02에만 직접 적용하고 채점·튜터 공통 호출 경로를 막지 않는다.

작업 순서는 코드 의존성으로 정한다. 기록 완료가 퀴즈 난이도의 선행이고, 채점 완료가 보충 생성의 선행이며, 보충 생성은 P-01의 일정 배치가 필요하다. 따라서 기존 '기록→퀴즈→온보딩 전체'의 단일 직렬 순서 대신 **P-01 같은 선행 기능을 앞당겨 병렬 처리**한다.

## 5. 최초 배정안과 후속 후보

먼저 오케스트레이터가 SYS-01/02를 완료한다. 모든 도메인의 상세 명세를 다시 작성하는 단계가 아니라 서로 호출할 자료 형식·소유권·결과 이벤트·미정 항목을 고정하는 단계다.

| 시점 | 실행 슬롯 A | 실행 슬롯 B | 실행 슬롯 C | 오케스트레이터 |
|---|---|---|---|---|
| 첫 병렬 실행 | R-01 범위 계산 | Q-01 퀴즈 ID/응답 | O-01 온보딩 상태 | 정책 POL-01/02/03, 공통 변경 조율 |
| 첫 완료 후 | R-02 또는 R-03 | Q-02 또는 O-02 | 완료된 task 리뷰 | 리뷰 통과분 통합, 다음 기준 SHA 발급 |
| 이후 준비된 후보 | D-01/R-04/B-01 | Q-03/Q-04/S-01 | M-01/P-01/SYS-04 중 준비된 작업 | 의존성과 파일 경합에 따라 한 자리씩 재배정 |

표의 같은 줄은 모두 동시에 끝난다는 일정 약속이 아니다. Q-02/SYS-04/R-04처럼 schema를 바꾸는 task는 별도 queue로 직렬화한다. R-02/R-03은 `today.py`가 겹치므로 같은 시점에 쓰기 배정하지 않는다. Q-03/Q-07은 기존 `quiz.py`/라우터 변경이 겹치면 순서를 맞춘다.

수치 정책 확인이 늦으면 온보딩 일정·답안 저장·범위 계산·오답 조회 같은 준비된 작업으로 슬롯을 채운다. 리뷰가 밀리면 신규 착수를 늘리지 않고 리뷰를 먼저 처리한다.

## 6. Git·파일·migration 운영

- 후속 통합 후보는 `integration/contract-v1`, 시작 앱 기준은 PR #13의 `f47eac6`이다. 실제 생성은 **이 계획 문서 커밋까지 포함한 `docs/development-task-plan` HEAD**에서 한다. 이후 root는 통합 worktree의 task registry를 관리해 계획이 이전 작업트리에만 남지 않게 한다. 이 문서 작성만으로 통합 브랜치를 만들거나 기존 PR을 병합하지 않는다.
- 각 task는 전용 worktree와 브랜치를 사용한다. 예: `feat/study-record-ranges`, `fix/quiz-item-identity`, `feat/onboarding-state`. root의 BE/FE/AI 작업트리와 다른 에이전트의 작업트리를 checkout/stash/reset하지 않는다.
- task PR은 통합 브랜치를 대상으로 하고, 통합 브랜치는 기존 PR #13 위의 후속 스택으로 관리한다. 해당 부모가 main에 반영되면 실제 diff를 확인해 기반을 갱신한다. 선행 task가 통합되어야 다음 task의 base SHA를 발급한다.
- 공개 전 브랜치만 필요한 rebase를 고려한다. 공개 후 부모 변경은 merge 반영을 기본으로 하며 임의 force push를 하지 않는다. 같은 변경을 merge와 cherry-pick으로 중복 반영하지 않는다.
- **원자 단위 완성 즉시 커밋**한다. task 전체가 끝날 때까지 커밋을 미루지 않는다. 각 커밋은 한 목적이며 테스트를 함께 포함한다. 서로 다른 도메인, 공통 인프라, 기존 테스트 보정은 분리한다. `git add -f` 금지.
- `schema/erd.dbml`, 생성 모델, generator, `migrations/versions/`는 전역 schema 자원이다. 수정 전에 오케스트레이터가 revision/down_revision과 쓰기 순서를 예약한다. 이미 배포한 revision은 변경하지 않는다. 통합 결과는 Alembic 단일 head여야 한다.
- `app/main.py`, FE `endpoints.js`/`queryKeys.js`, 테스트 공통 fixture, CI, AI gitlink는 통합 전용이다. 실행자는 필요한 최소 변경을 제안하고 오케스트레이터가 해당 task에 한시적 수정 권한을 부여하거나 작업트리에 반영한다. **라우트 등록이 빠진 API는 완료가 아니다.** 등록·테스트까지 들어간 원자 커밋으로 마무리한다.
- 기존 `StudyData`/`QuizService`/`Planner`는 담당 task 외 수정 금지. 여러 작업이 필요하면 새 도메인 모듈로 분리하고 기존 모듈 연결은 한 담당자가 순차 처리한다. task 관련 없는 대규모 리팩터링은 하지 않는다.
- 테스트 DB는 작업별 독립 schema, 실행 서버는 작업별 포트를 사용한다. 공통 venv 패키지를 여러 에이전트가 동시에 변경하지 않는다. dependency 변경이 필요하면 별도 인프라 변경으로 제안한다.
- FE는 기존 dev 흐름과 담당자 변경을 보존한다. 큰 API 연결 수정 전 기준 SHA/보관 브랜치를 남기며 G-1의 흑백 상태 구분도 검사한다. AI 수정은 AI worktree에서 별도 PR로 검증하고 BE는 검증된 커밋만 pin한다.

## 7. 상태·리뷰·완료 기준

task 상태는 `planned → running → review → integrated`이며, 보완 필요 시 `review → running`으로 돌아간다. 외부 조건 때문에 진행 불가능할 때만 사유를 적어 `waiting`으로 둔다. 준비 여부는 선행 task와 파일 소유권으로 계산하며 별도 중복 상태를 만들지 않는다.

1. 실행자는 대상 테스트, 실패 경계, 실제 검증한 HEAD SHA, 커밋별 목적, 미해결 항목을 반환한다.
2. 다른 에이전트 또는 오케스트레이터가 immutable SHA를 검토한다. 명세 불일치·소유권·트랜잭션·동시성·재시도를 확인하고 결과는 한국어로 작성한다.
3. 수정이 생기면 바뀐 SHA의 영향 테스트를 다시 실행한다. 변경 전 검토를 새 HEAD 승인으로 간주하지 않는다.
4. root만 통합하고 실제 통합 SHA에서 필요한 회귀 검사를 확인한 후 `integrated`로 표시한다. 구현자 메시지나 로컬 테스트 성공만으로 상태를 올리지 않는다.
5. task 코드·테스트·문서·실제 라우트 연결·FE 전달 차이가 완료 조건을 충족해야 한다. 다른 task 몫을 임의 stub으로 채워 성공처럼 반환하지 않는다.

검증 범위:

- 변경한 도메인은 정상/빈 값/경계/타인 객체/재시도/롤백을 포함한다. 동시성·영속 변경은 SQLite와 PostgreSQL에서 확인한다.
- BE는 CI와 동일하게 `python -m pytest -q tests`를 사용한다. 범위 없는 pytest가 private AI submodule의 키 필수 테스트까지 수집하는 점을 구분한다.
- task 단계에서는 영향 테스트, 통합 체크포인트에서는 BE 전체 회귀와 schema 검사. 같은 SHA의 동일 검사를 이유 없이 반복하지 않는다.
- 문서 경로 검사와 런타임 계약 검사를 구분한다. 새 기능에 맞춘 요청/응답 모델·실제 API 검증이 필요하다.
- FE 코드 변경은 `npm run check`와 실제 화면 검증을 포함한다. 브라우저 자동화는 사용자 지시대로 인앱 브라우저를 우선한다.
- 실제 AI 호출 없이 수행한 검사를 실호출 검증으로 표현하지 않는다. 키 값은 채팅·문서·로그에 기록하지 않는다.

## 8. 인수인계 형식

배정 시 task JSON 한 항목과 다음 정보를 전달한다. 긴 전체 대화 대신 필요한 계약·경로·판단만 제공한다.

```text
Task: R-02 / 범위별 기록 저장·정정 API
Worktree / branch / base SHA: root가 실제 생성 후 기입
선행 완료 SHA: R-01=...
읽을 계약: docs/api/study.md, common.md, 해당 task card
수정 허용 경로 / 통합 전용 경로: task card + 이번에 허용한 최소 변경
완료 조건 / 필수 엣지케이스: task card
검증 환경: 독립 SQLite/PG schema, 사용 포트
하지 않을 일: 타 task/타 worktree 변경, 배포, main merge, 추가 agent 생성
반환: HEAD SHA, 원자 커밋 목록, 테스트 결과, 계약 차이, 남은 위험/의존성
```

반환에는 사용자나 동료에게 메시지를 보냈다는 가정을 넣지 않는다. FE 전달 문서는 준비하되 별도 외부 전송은 명시적 지시가 있을 때 수행한다.

## 9. 통합·배포 체크포인트

전체 task가 끝날 때까지 배포를 미루지는 않는다. 다만 구현 완료, 통합 완료, 배포 완료를 각각 기록한다.

| 체크포인트 | 최소 완료 범위 | 검증·표시 |
|---|---|---|
| 기존 완료분 승격 | PR #13 리뷰/회귀, 배포 인프라 경로 확인 | 기록 정정 1단계만 추가 배포했다는 범위를 명시 |
| 기록 안정화 | R-01~04, D-01~03, B-01 및 그 선행 task | 복합 범위/정정/재시도/회독/홈 집계. 미완성 다른 도메인을 완료로 표시하지 않음 |
| 퀴즈·학습 시연 | Q/S/V/L과 해당 FE 연결 중 릴리스에 포함할 task | 답 보존·저장 채점·회복·오답·재계획 시연. 선택된 manifest만 검증/배포 |
| 빈 계정 전체 흐름 | QA-03과 모든 선행, 실제 AI 자격/품질 확인 | 온보딩→자료→계획→일반 날짜, mock 해제 확인 |
| 전체 계약 완료 | 모든 필수 task가 integrated, QA-02/03 통과 | REL-01. 선택 OPT-01은 완료 조건에서 제외 |

중간 배포는 root가 명시적인 release manifest에 포함 task와 BE/AI/FE SHA, DB revision, 성공한 검증을 고정한다. 배포 task에는 그 SHA만 전달하며 개발 중인 새 HEAD를 가져가지 않는다. 전체 완료 REL-01의 선행 조건을 중간 배포 성공으로 생략하지 않는다.

RPI 배포는 기존대로 GitHub-hosted ARM64 빌드 → RPI5 runner → RPI4 Compose다. 운영 변경은 root가 지정한 배포 에이전트 한 명만 실행한다. 대상·포트·기존 사용자 데이터를 보존하고, 쓰기 중지 시점 백업·실제 digest·DB revision·공개 동작·복구 절차를 작업공간 루트 `RPI-DEPLOYMENT-ROLLBACK.md`에 남긴다. FE 배포 경로가 확인되지 않은 상태에서 호스팅 서비스를 임의로 바꾸지 않는다.

## 10. 계획 자체의 검증

- 필수82 task + 선택1 task의 ID 중복과 존재하지 않는 의존성이 없다.
- 의존성 그래프에 순환이 없다. 모든 필수 task는 REL-01의 선행 그래프에 포함된다.
- 계약 registry 76개 경로를 기존 완료11개와 후속 담당65개에 모두 매핑했다. 선택 경로2개는 OPT-01 하나에 묶었다.
- 첫 병렬 R-01/Q-01/O-01은 파일 범위와 named resource가 겹치지 않는다.
- 계획 문서는 구현·운영 테스트를 대체하지 않는다. 실행 시 최신 원격 상태와 계약 변화에 맞춰 task를 추가·분할하며 근거를 남긴다.
