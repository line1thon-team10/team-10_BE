# O-02 초기 온보딩 일정 인계

## 구현 범위와 호출 계약

다음 네 경로는 실제 DB의 사용자 소유 일정을 조회·저장한다. 모든 성공 응답은 `docs/api/onboarding.md`의 Calendar 형식을 공통으로 사용한다.

| 경로 | 동작 |
| --- | --- |
| `GET /api/onboarding/calendar` | 사용자 기준 이번 주와 일정·시험·가용 시간 조회 |
| `POST /api/onboarding/events` | 초기 draft의 일정 생성 |
| `PATCH /api/onboarding/events/:id` | 초기 draft의 일정 부분 수정 |
| `DELETE /api/onboarding/events/:id` | 초기 draft의 일정 삭제 |

일반 CRUD의 `addedId`는 항상 `null`, 각 `Event.added`는 `false`다. 명세상 이 강조 표시는 `/events/voice`가 만든 일정에만 사용한다. 현재 FE `toCalendar`도 누락된 `addedId`를 `null`로 정규화하므로 일반 CRUD와 호환된다. `/voice`와 S1 자연어 대화는 O-03 후속이며 성공 stub을 만들지 않았다. 승인된 계획의 일정 변경은 C 계열 작업 범위다.

GET에는 주·과목 선택 query가 없다. 서버의 `today_for(user)`를 한 번 사용해 `today`와 월요일 `weekStart`를 계산한다. 데모는 `users.demo_date`, 일반 사용자는 `users.timezone`의 실제 날짜를 사용한다. 빈 계정도 정상 응답하며 고정 시간 0분, 자유 시간 6,300분이다. `events`는 소유한 삭제되지 않은 일반 일정 시리즈 전체, `exams`는 소유한 draft/active 과목 중 시험일이 있는 과목 전체다. 다른 사용자 소유 과목에 잘못 연결된 이벤트는 반환하지 않는다. 시험은 sidebar 정보이며 고정 일정 분량에 중복 합산하지 않는다.

## 입력 검증과 부분 수정

- POST는 `kind`, `title`, `start`, `end`와 `days` 또는 `date`가 필수다. `kind`는 `class/job/meet/other`, `days`는 비어 있지 않고 중복 없는 정수 1..7이며 bool·실수·숫자 문자열을 허용하지 않는다. 정상 요일은 정렬해 반환한다.
- `date`는 유효한 `YYYY-MM-DD`, 시각은 `HH:mm`이며 `start < end`를 요구한다. `24:00`, 초 단위, 같은 시작·종료 시각, 자정을 넘는 일정은 422다. 자정을 넘으면 명세에 따라 날짜별 일정으로 나누어 입력한다.
- 이름이 비었거나 공백뿐이면 공통 `EMPTY` 400이다. NUL과 고립 surrogate는 PostgreSQL/SQLite 저장 전에 `INVALID_INPUT` 422로 거절한다. 임의 필드, 잘못된 형식도 422다.
- PATCH는 생략한 필드를 현재 값과 병합한 뒤 POST와 같은 전체 조건을 검증한다. `{}` 또는 기존과 동일한 값은 revision을 올리지 않는다. `kind/title/start/end`의 명시적 null은 거절한다.
- `days`와 `date`의 명시적 null은 FE `EventModal` 입력과 맞춰 허용한다. 반복→단발은 `{days:null,date:"2026-11-14"}`, 단발→반복은 `{date:null,days:[1,3]}`처럼 반대 필드를 명시적으로 비워야 한다. 누락된 반대 필드를 서버가 임의로 지우지 않는다.
- 존재하지 않는 사용자·인증 누락은 공통 401, 잘못된 UUID 경로 형식은 422, 유효한 UUID이지만 타인·삭제·미존재 일정은 `EVENT_NOT_FOUND` 404다.

## 반복 범위·예외·시간대

새 반복 일정은 사용자의 이번 주 월요일부터 첫 선택 요일을 찾아 시작한다. 수요일 요청에 월·수를 선택하면 이번 주 월요일이 첫 발생일이다. 이후 단순 주간 RRULE과 UTC 시작·종료 시각을 저장한다.

기존 일정의 이름·종류·시각만 부분 수정하면 첫 발생일, 반복 종료일, 예외 행을 보존한다. 변경하지 않은 시각은 기존 초·마이크로초까지 유지한다. 반복 요일을 바꾸면 기존 첫 발생일 이상인 첫 선택 요일을 새 시작으로 사용하고 기존 종료일을 보존한다. 단발→반복은 새 반복 일정과 같은 이번 주 기준을 사용한다. 반복→단발은 반복 규칙·종료일을 비운다. 예외 행은 보존하며 바뀐 시리즈에서 유효하지 않은 원래 회차의 예외는 가용 시간에 적용하지 않는다. 삭제는 parent의 `deleted_at`과 revision을 갱신하고 예외 행은 유지한다.

날짜·요일만 옮겨도 생략하거나 기존 표시와 같은 시각의 초·마이크로초를 보존한다.
PATCH의 시간 순서는 HH:mm 표시 문자열이 아닌 최종 실제 instant로 검사한다.
예를 들어09:00:10~09:00:50은 둘 다09:00으로 표시되지만 유효한 기존 구간이므로
이름 수정·빈 PATCH·같은 표시값 재전송을 허용한다. 실제로 역전되는 시각 변경은422다.
새 POST와 새로 변경하는 일정은 자정 넘김을 금지하며, 이미 저장된 다일 구간의
이름만 바꾸는 요청에는 새 생성 제한을 소급하지 않는다.

새 입력은 사용자 시간대의 날짜·시각을 실제 UTC instant로 바꾼 후 저장한다. 조회 시 SQLite의 naive timestamp도 UTC로 해석해 사용자 시간대로 돌린다. 단발 날짜가 UTC 전날/다음 날에 저장되어도 응답의 로컬 날짜는 유지된다. 최초 시각 자체가 DST로 존재하지 않거나 두 instant를 가리키는 경우는 임의 fold를 선택하지 않고 422로 거절한다.

기존 `seed.loader._at()`는 KST aware 값을 그대로 SQLite에 저장해 offset이 사라지고, UTC로 읽으면 화면이 9시간 뒤로 밀렸다. 별도 수정 커밋에서 `_at()`만 UTC로 정규화했다. 시드의 종류·요일·시각 등 다른 값은 바꾸지 않았다. day9의 실제 `GET /api/onboarding`와 `GET /api/onboarding/calendar`에서 시작·종료 시각 및 UTC 저장을 두 DB로 검증한다. 과거에 이미 잘못 저장된 SQLite 데이터는 정상 UTC 데이터와 구분할 근거가 없으므로 일괄 9시간 이동하지 않는다. 수정된 코드로 다시 시드한 데이터부터 올바르게 저장된다.

## 주간 요약과 FE 차이

매일 로컬 08:00~23:00의 900분 창을 사용한다. 해당 주의 실제 발생 회차를 펼친 후 일정 합집합만 차감한다. 반복 시작일·종료일을 포함해 부분 주를 계산하며, 취소·이동 예외도 적용한다. 이전 주의 회차가 이번 주로 이동한 경우와 이번 주의 회차가 다른 주로 이동한 경우를 모두 반영한다. 시간 창 밖의 분량과 겹침을 중복 차감하지 않아 `fixedMinutes + freeMinutes = 6300`이며 두 값은 음수가 되지 않는다.

예를 들어 같은 날 06:00~09:00, 08:30~09:30, 09:00~10:00은 08:00~10:00 합집합인 120분이다. 여기에 22:00~23:30이 있으면 고정 시간은 180분, 주간 자유 시간은 6,120분이다. FE mock은 단순 길이 합을 빼므로 겹침·시간 창 밖의 일정에서 값이 달랐다. BE는 확정 명세의 합집합 규칙을 적용했다.

기존 `Event` 응답에는 반복 시작일·종료일·회차 예외 필드가 없다. 따라서 기존 시리즈를 그대로 반환하는 S2 `toFc` 화면은 부분 주·취소·이동을 정확히 그릴 수 없지만, 서버 summary는 실제 회차로 계산한다. 임의 occurrence ID나 응답 필드를 추가하지 않았다. 승인 후 실제 회차 화면은 C-01 계약에서 해결해야 한다. 또한 FE 화면의 `slotMaxTime`은 24:00이지만 학습 가능 시간 계산의 상한은 확정 명세대로 23:00이다. 시각 23:00 이후 일정 자체는 저장할 수 있으며 자유 시간을 깎지 않는다.

## 승인 경합과 원자성

생성·수정·삭제는 공통 사용자 잠금을 얻은 뒤 최신 사용자 상태를 다시 읽는다. `onboarding_status != draft`이거나 이미 계획이 있으면 `ONBOARDING_COMPLETED` 409다. 새 draft 과목을 추가해도 초기 일정 수정 권한이 다시 열리지 않는다. 잠금 경합은 `REQUEST_IN_PROGRESS` 409로 반환한다. 이후 승인 커밋 뒤 재시도하면 완료 상태를 확인하므로 오래된 인증 스냅샷으로 우회할 수 없다. 승인을 수행하는 후속 경로도 같은 `lock_user` 계약을 유지해야 한다.

요청 DB transaction 안에서 입력 병합·검증, 쓰기, 최종 calendar 응답 생성을 수행한다. 저장 후 응답 계산이 실패해도 요청 전체가 rollback된다. 서비스·저장소는 caller Connection을 commit/close하지 않는다. GET은 승인 후에도 허용하며 일정·계획을 변경하지 않는다. 승인 당일 새 과목을 추가한 경우 기존 이벤트와 plan revision이 그대로임을 서비스와 HTTP 모두에서 검증했다.

## 검증

`tests/test_onboarding_events.py`는 엄격 입력, 빈 계정, 날짜·주 경계, 겹침·시간 창, 반복 시작/종료/예외, 소유권, 부분 수정, 실제 DB 잠금 경합, 승인 상태 재조회, 서비스/HTTP rollback, NUL/surrogate, UTC 변환, demo/일반 날짜, 실제 CRUD와 day9 GET을 다룬다. `tests/test_seed_calendar_time.py`는 기존 seed 시간대 결함을 별도로 고정한다.

위 두 파일은 SQLite/PostgreSQL을 함께 활성화한 실행에서 **171 passed**다. 기존 온보딩 API/상태, demo seed/focus/quiz/state/next-day/package, API 등록 계약, 응답 캐시 회귀는 별도 실행에서 **213 passed**다. 중복 없는 관련 검증 합계는 384건이다. 외부 라이브러리의 기존 SWIG deprecation 경고 외 실패·skip은 없다.

독립 검토에서 PATCH의 HH:mm 변환이 기존 정밀도를 잃는 문제를 발견해 보완했다.
기존 두 파일과 새로운 실제 HTTP 경계24건을 합친 최종 수정 검증은 SQLite/PG
**195 passed**다. 원래 독립 재현과 DST/다일 구간 경계는 수정 SHA에서 다시 확인한다.

외부 AI 호출과 새로운 schema 변경은 없다. 검증에는 임시 SQLite DB와 격리된 로컬 PostgreSQL schema를 사용한다. 이 구현만으로 O-03 자연어 해석, 승인 후 일정 재배치 또는 C-01 회차 화면을 완료했다고 간주하지 않는다.
